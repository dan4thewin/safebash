## Resolution (DG, 2026-05-26)

> Make status.md dynamically updated.

Implementation in [r47-status-md-from-spec-db](r47-status-md-from-spec-db).
Approach: delimited block regenerated by `mk status` (called from
`mk test`) so prose context is preserved but the live numbers can't
drift. Same pattern can be reused for Brush totals in `audit.md`.

`notes/status.md` is the most visible health signal in the repo. Today
it is hand-edited and goes stale on every session that doesn't update
it. At 2026-05-26 it says "267 passing / 15 failing" while spec.db
reports 285/285 (gap of two sessions).

## What needs to be decided

Options:

1. **Generate the "current spec status" block** from `spec.db`
   automatically (`mk status` overwrites a delimited section in
   status.md, run as part of `mk test`).
2. **Keep hand-edited** but add a CI/`mk check` assertion that fails
   if the numbers in status.md don't match spec.db.
3. **Replace status.md** with a generated dashboard at
   `notes/status-spec.md` and let `notes/status.md` be pure prose
   (current-priority, just-completed, next-up).

## Why DG should decide

This shapes what "ground truth for project status" means. Generated
artifacts have less narrative; hand-edited files drift. Option 3 is a
hybrid that matches how the journal already works (chronicle vs. live
counts).

## Inputs for the decision

- `notes/status.md` today
- `spec.db` schema: `test_status` view exists; counts by status are
  one SELECT away
- Cargo test counts and Brush counts are also out of date in
  `audit.md` / similar files — same drift problem at smaller scale

## Output

A short note (DD or amendment to `notes/architecture.md`) that records
the choice. Gates `r47-status-md-from-spec-db` (P4).
