## CRITICAL FINDINGS (Immediate Action Required)

### **F1: Herestring with tainted expansion marked clean** [CRITICAL]

**Bypass:** `read var <<< "$tainted"` marks `var` as clean despite reading tainted data.

```bash
#!/bin/bash
x=$(getenv UNTRUSTED)
read y <<< "$x"
echo "$y"  # y is tainted but marked clean — NO SB4020
```

**Why compiler doesn't catch it:**  
`taint.rs` line 199-218: `handle_read` checks for presence of `herestring_redirect` node and marks the target variable clean, but **never inspects the herestring content** for tainted expansions. The check is structural (is there a `<<<` redirect?) not semantic (does the herestring contain tainted data?).

**Fix:** Parse herestring body, scan for expansions, mark target tainted if any expansion reads tainted data.

---

### **F2: Indirect expansion bypass via ${!var}** [CRITICAL]

**Bypass:** `${!varname}` where `varname` contains the name of a tainted variable.

```bash
#!/bin/bash
secret=$(getenv PASSWORD)
varname="secret"
echo "${!varname}"  # Reads $secret without SB4020
```

**Why compiler doesn't catch it:**  
`taint.rs` has **no handling for indirect expansion**. `extract_expansion_var` looks for a `variable_name` child node but doesn't recognize the `!` operator. Tree-sitter parses `${!x}` with an indirection operator node — the code reads the literal variable `x`, not the variable whose name is stored in `x`.

**Fix:** Detect indirect expansion operator in `expansion` nodes, recursively resolve the indirection, check taint status of the target variable.

---

### **F3: Nameref bypass via declare -n** [CRITICAL]

**Bypass:** `declare -n ref=tainted; echo $ref` — nameref points to tainted var but is itself marked clean.

```bash
#!/bin/bash
secret=$(getenv TOKEN)
declare -n ref=secret
echo "$ref"  # ref → $secret, but ref is clean — NO SB4020
```

**Why compiler doesn't catch it:**  
`taint.rs` line 189: `handle_declaration` marks all declared variables as clean without tracking **nameref semantics**. Reading `$ref` should dereference to `$secret` and inherit its taint status, but the current implementation treats `ref` as an independent clean variable.

**Fix:** Track nameref relationships in `TaintTracker`, resolve aliases when checking taint status.

---

### **F4: Tautological bless test always passes** [CRITICAL]

**Bypass:** `bless x [[ 1 == 1 ]]` — test always succeeds without validating `x`.

```bash
#!/bin/bash
x=$(getenv MALICIOUS)
bless x [[ 1 == 1 ]]
echo "$x"  # x blessed without inspection
```

**Why compiler doesn't catch it:**  
`taint.rs` line 254-280: `handle_bless` walks the test expression to allow reads of the variable being blessed, then unconditionally marks it blessed. **No verification that the test actually constrains the variable value**. A tautology like `[[ 1 == 1 ]]` or `[[ -n "literal" ]]` blesses the variable without ever evaluating it.

**Fix:** Static analysis to ensure test expression references the variable being blessed. Reject tautologies at compile time or require runtime enforcement to actually test the value.

---

### **F5: Bless wrong variable** [CRITICAL]

**Bypass:** `bless safe [[ -n $safe ]]; echo $evil` — bless one var, use another.

```bash
#!/bin/bash
evil=$(getenv PAYLOAD)
safe="literal"
bless safe [[ -n $safe ]]
echo "$evil"  # evil never blessed — might bypass if analyzer confused
```

**Why compiler doesn't catch it:**  
While `is_tainted` should still catch this, the bless mechanism **doesn't verify the test expression references the variable being blessed**. Could write `bless x [[ -n $y ]]` and `x` would be marked blessed despite the test never mentioning it.

**Fix:** Parse test expression, verify it contains at least one reference to the variable being blessed. Reject if test doesn't mention the variable.

---

### **F17: Array element taint not tracked separately** [CRITICAL]

**Bypass:** Array elements can be tainted while array variable is clean, or vice versa.

```bash
#!/bin/bash
array clean=(a b c)
evil=$(getenv IDX)
clean[$evil]="overwrite"  # Tainted index, clean array name
echo "${clean[0]}"  # Element lookup might use tainted key
```

**Why compiler doesn't catch it:**  
`taint.rs` tracks taint status per **variable name**, not per **array element**. An array populated by `mapfile` has tainted elements but the variable name `lines` itself might not be marked tainted. Conversely, subscript assignment with a tainted index corrupts the key space but the array variable remains clean.

**Fix:** Track array taint separately: whole-array taint (from mapfile) vs element-level taint (from subscript assigns). Mark array variable tainted if any element is tainted.

## HIGH SEVERITY

### **F6: TOCTOU — Re-assign after bless** [HIGH]

**Bypass:** Bless, then re-assign from different tainted source before use.

```bash
#!/bin/bash
x=$(getenv A)
bless x [[ -n $x ]]
x=$(getenv B)  # Re-tainted
echo "$x"  # Should reject but might be lowered already
```

**Why it might bypass:** Sequential taint analysis updates state on re-assignment (line 398), so this *should* work. Test `taint_retaint_after_bless` expects SB4020. But verify all lowering paths re-check taint before emitting reads.

**Severity:** Test exists and expects rejection, but worth verifying codegen doesn't cache taint status.

### **F8: For-loop over tainted array elements** [HIGH]

```bash
#!/bin/bash
array lines
mapfile -t lines < /dev/stdin
for x in "${lines[@]}"; do
  echo "$x"  # x should be tainted
done
```

**Why it might bypass:** `for_statement` handler checks `expr_has_tainted_read` on the `"${lines[@]}"` expansion, which looks at the array **variable** `lines`, not individual elements. If `lines` itself isn't marked tainted (only its elements are), the loop var `x` could be marked clean.

### **F9: Shift bypasses positional range check** [HIGH]

```bash
#!/bin/bash
fn() {
  shift
  echo "$1"  # Out of bounds if called with 1 arg
}
fn "only-arg"
```

**Why compiler doesn't catch it:** `collect_max_positional` performs **static analysis** of positional references but doesn't track `shift` commands that change effective argc at runtime. A function that shifts N times then reads `$1` could access out-of-range memory.

**Fix:** Track shift in static analysis or make positional access bounds-checked at runtime.
