### Findings (validator misses real dynamic-exec forms)

1) **`eval` invoked indirectly** — **CRITICAL**  
**What:** still enables runtime code execution via `eval`, without diagnostics.  
**Why missed:** `DynamicExecution` only matches when the *first* command word is exactly `eval` (`dynamic_execution.rs`). It does not inspect wrapper builtins (e.g., `builtin`/`command` invoking `eval` as an argument) nor normalize the “actual executed word”.

2) **Dynamic command names inside a `word` node** — **CRITICAL**  
**What:** variable-as-command / computed command names can pass without SB4004.  
**Why missed:** SB4004 only fires when `command_name.child(0).kind() != "word"`. But a `word` can still *contain expansions* (concatenation, quoted forms, etc.), and the rule never checks for expansions *within* the `word`.

3) **`source` / `.` marker bypass via indirection/normalization gaps** — **HIGH**  
**What:** can avoid SB4002 marker so the compiler may skip the “safe kvp loader” transform described in `exp/SUBSET.md`.  
**Why missed:** same root cause as above: only the first literal word is checked; wrapper/quoted/concatenated spellings aren’t recognized as `source`/`.`.

### Defensive fixes to add
- Implement a “static command word” extractor: if the command word contains *any* expansion/substitution, emit **SB4004** (or a new reject code) even if the outer node is `word`. If it’s purely literal (including quoted literal), normalize and compare to `eval`/`source`/`.`.
- Add wrapper detection: if first static word is `builtin`/`command`, analyze the next word as the effective command for SB4001/SB4002/SB4004.
- Add integration tests for these cases (currently only `$cmd`/`${cmd}` are covered in `tests/integration.rs`).
