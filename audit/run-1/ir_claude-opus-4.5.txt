# Bash-to-IR Semantic Fidelity Audit

## Finding 1: Heredoc Expansion Mode Lost

**Bash construct:**
```bash
cat <<EOF       # Variables expanded
Hello $USER
EOF

cat <<'EOF'     # Variables NOT expanded (literal)
Hello $USER
EOF

cat <<-EOF      # Tabs stripped from content
	indented
EOF
```

**What Bash does:** `<<EOF` expands variables, `<<'EOF'` treats content literally, `<<-EOF` strips leading tabs.

**What IR represents:** `RedirectOp::HereDoc` with no flag distinguishing quoted vs unquoted delimiter or dash prefix. The delimiter and content are lowered via `lower_expr()` but quoting distinction is lost.

**Impact:** Compiler cannot know whether to expand variables in heredoc content or strip tabs.

**Severity:** HIGH — Variables will be incorrectly expanded or left literal.

## Finding 2: Process Substitution Not Handled

**Bash construct:**
```bash
diff <(cmd1) <(cmd2)
tee >(logger)
```

**What Bash does:** `<()` runs cmd in a subshell, provides a `/dev/fd/N` path. `>()` provides a writable fd.

**What IR represents:** Not represented. Falls through to the default case at line 690-693, becomes `ExprKind::Literal("<(cmd1)")` — the raw text.

**Impact:** Process substitutions treated as literal filenames; commands will fail to find `/dev/fd/...`.

**Severity:** HIGH — Behavior completely broken.

## Finding 3: Brace Expansion Not Distinguished

**Bash construct:**
```bash
echo {a,b,c}
echo file{1..10}.txt
```

**What Bash does:** Expands to `a b c` or `file1.txt file2.txt ... file10.txt` before globbing.

**What IR represents:** `ExprKind::Literal("{a,b,c}")` — raw text, indistinguishable from a literal brace pattern.

**Impact:** Brace expansion won't occur; `{a,b,c}` passed as a single argument.

**Severity:** HIGH — Multiple-argument expansion becomes single-argument literal.

## Finding 4: `;;;&` Case Fallthrough Variant Not Captured

**Bash construct:**
```bash
case $x in
  a) echo a ;;    # stop
  b) echo b ;&    # fallthrough to next body
  c) echo c ;;&   # fallthrough to test next pattern
esac
```

**What Bash does:** `;;` stops, `;&` falls through unconditionally, `;;&` tests the next pattern (Bash 4.0+).

**What IR represents:** `CaseItem.fallthrough: bool` only distinguishes `;;` vs `;&`. The `;;&` variant is conflated with `;&`.

**Impact:** `;;&&` (continue pattern matching) treated as unconditional fallthrough.

**Severity:** MEDIUM — Different control flow for `;;&` cases.

## Finding 7: Extended Glob Semantics Not Preserved

**Bash construct:**

**What Bash does:** When `extglob` is set, these are special patterns.

**What IR represents:** `ExprKind::Literal("?(pattern)")` — raw text. The code at line 601 handles `extglob_pattern` but just captures the text.

**Impact:** No distinction between extended glob and literal text containing `?()`.

**Severity:** MEDIUM — Depends on whether extglob is enabled at runtime.

## Finding 9: `declare` Flags Not Semantically Interpreted

**Bash construct:**
```bash

declare -a arr      # indexed array
declare -A hash     # associative array
declare -r const=1  # readonly

```

**What Bash does:** Each flag changes variable semantics (integer arithmetic, array type, etc.).

**What IR represents:** Flags stored as `Vec<String>` (line 99), but not interpreted. `-i` (integer) is just a string, not a semantic marker.

**Impact:** Compiler cannot know `$((num + 1))` uses integer semantics, or that `hash[key]` is associative.

**Severity:** MEDIUM — Loss of type information for analysis.

## Finding 11: Arithmetic `let` and `(())` Constructs

**Bash construct:**
```bash
let x=1+2
let "x += 5"
((x++))
(( y = x * 2 ))
```

**What Bash does:** `let` and `(())` perform arithmetic; `(())` as a statement sets exit code.

**What IR represents:** `let` becomes a `Command` with name "let". `(())` falls through (it's an `arithmetic_expansion` at statement level, not expression level).

**Impact:** `(( x++ ))` may be dropped or misrepresented; no arithmetic statement type.

**Severity:** MEDIUM — Arithmetic side effects not modeled.

## Finding 12: `[` vs `[[` Not Distinguished

**Bash construct:**
```bash
[ -f "$file" ]    # POSIX test, word splitting applies
[[ -f $file ]]    # Bash test, no word splitting
[[ $x =~ regex ]] # Regex only in [[
```

**What Bash does:** `[` is a command with different quoting rules; `[[` is a keyword with special parsing.

**What IR represents:** Both render to `ExprKind::Test` or a command with name `[[` (lines 86-95, 286-290).

**Impact:** Quoting requirements differ; regex `=~` only valid in `[[`.

**Severity:** MEDIUM — Semantic conflation.

## Finding 13: Here-String Content Type

**Bash construct:**
```bash
cat <<< "expanded $var"
cat <<< 'literal'
cat <<< $var
```

**What Bash does:** Expands the word (double-quoted context by default), feeds as stdin.

**What IR represents:** `RedirectOp::HereString` with target lowered via `lower_expr()`. The quoting is preserved in `target`, but `$var` without quotes behaves like double-quoted.

**Impact:** `cat <<< $var` — unquoted variable behaves as quoted but IR shows `SimpleExpansion`.

**Severity:** LOW — Usually correct, edge cases around word splitting differ.
